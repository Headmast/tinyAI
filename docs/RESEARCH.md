# Исследовательские эксперименты TinyAI

> 5 экспериментов для улучшения качества системы

---

## Эксперимент 1: Гибридный поиск (BM25 + векторный)

**Гипотеза:** Комбинация BM25 и векторного поиска даёт +15–20% к recall@5
по сравнению с чисто векторным поиском.

**Обоснование:** Векторный поиск хорошо улавливает семантику, но может
пропускать точные термины. BM25 отлично находит keyword-совпадения.
Комбинация (reciprocal rank fusion) объединяет оба преимущества.

**Метрики:**
- recall@5 — доля релевантных документов в top-5
- precision@5 — точность в top-5
- MRR (Mean Reciprocal Rank)

**План реализации:**
1. Добавить BM25-индекс в `rag/search.py` (библиотека `rank_bm25`)
2. Реализовать Reciprocal Rank Fusion (RRF) для слияния двух рейтингов
3. Создать бенчмарк из 20 вопросов + ground truth документов из `rag_data/`
4. Сравнить: vector-only vs BM25-only vs hybrid
5. Замерить latency overhead

**Ожидаемый результат:** hybrid > vector-only на 15–20% recall, с < 50ms
дополнительной задержки.

## Эксперимент 2: Влияние размера чанков на качество RAG

**Гипотеза:** Чанки 256 токенов с overlap=64 дают лучшее качество для
фактических вопросов, чем текущие 512/64.

**Обоснование:** Меньшие чанки точнее фокусируются на конкретных фактах,
снижая «разбавление контекста» нерелевантным текстом.

**Метрики:**
- faithfulness — ответ опирается на предоставленный контекст (LLM-судья)
- relevance — чанки релевантны вопросу
- answer correctness — сравнение с ground truth

**План реализации:**
1. Параметризовать `FixedSizeChunker` в бенчмарке
2. Тестовые конфигурации: 128/32, 256/64, 512/64, 512/128, 1024/128
3. Набор из 15 вопросов: 5 фактических, 5 аналитических, 5 обзорных
4. Индексировать одни и те же документы с разным chunking
5. Сравнить качество ответов (LLM-as-judge)

**Ожидаемый результат:** 256/64 лучше для фактических вопросов,
512/128 лучше для аналитических.

## Эксперимент 3: Эффективность компрессии контекста

**Гипотеза:** Суммаризация при превышении 80% context window не ухудшает
качество ответов по сравнению с полным контекстом.

**Обоснование:** `ContextCompressor` в `news_agent/context_compressor.py`
сжимает историю диалога при приближении к лимиту токенов. Нужно проверить,
сохраняется ли когерентность.

**Метрики:**
- coherence score — оценивается LLM-судьёй по шкале 1–5
- information loss — сколько ключевых фактов утеряно после компрессии
- token savings — % экономии токенов

**План реализации:**
1. Создать 5 длинных диалогов (> 3000 токенов) с ключевыми фактами
2. Для каждого: полная версия vs сжатая версия
3. Задать 3 вопроса, зависящих от ранее упомянутых фактов
4. LLM-судья сравнивает ответы (blind evaluation)
5. Подсчитать % утерянных фактов

**Ожидаемый результат:** coherence ≥ 4.0/5.0 при экономии ≥ 40% токенов.

## Эксперимент 4: FSM vs свободное LLM-планирование

**Гипотеза:** FSM-агент журналиста (жёсткие переходы) более предсказуем,
но менее гибок, чем ReAct-агент с free-form planning.

**Обоснование:** `JournalistFSMAgent` следует фиксированным фазам
(planning → research → writing → review → done). ReAct-агент (`AgentLoop`)
выбирает шаги самостоятельно. Нужно сравнить оба подхода.

**Метрики:**
- success rate — % задач, доведённых до финала
- steps to completion — количество шагов
- output quality — оценка LLM-судьёй (1–5)
- invariant violations — нарушения редакционных правил
- human preference — какой результат предпочтителен

**План реализации:**
1. 10 тем для генерации статей
2. Каждую обрабатывают оба агента (FSM и ReAct)
3. Замерить метрики, собрать результаты
4. Blind-оценка парами LLM-судьёй
5. Статистический тест (Wilcoxon signed-rank)

**Ожидаемый результат:** FSM — выше success rate и меньше violations;
ReAct — разнообразнее и иногда качественнее.

## Эксперимент 5: Влияние персонализации на качество генерации

**Гипотеза:** Агент с user profile (аналитик vs журналист) получает
значимо более высокие оценки от целевой аудитории.

**Обоснование:** `PersonalizedAgent` в `memory_agent/personalized_agent.py`
адаптирует стиль под профиль пользователя. Нужно измерить реальный эффект.

**Метрики:**
- relevance to audience — оценка LLM-судьёй (1–5)
- style match — соответствие ожидаемому стилю
- preference — A/B тест (с профилем vs без)

**План реализации:**
1. 2 профиля: «Аналитик» (факты, данные, графики) и «Журналист» (истории, цитаты, яркость)
2. 5 тем для генерации контента
3. Каждая тема × 2 профиля × 2 режима (с профилем / без) = 20 текстов
4. LLM-судья оценивает каждый текст для каждой аудитории
5. Paired comparison: с профилем vs без для каждой аудитории

**Ожидаемый результат:** тексты с профилем получают +0.5–1.0 по шкале 1–5
для целевой аудитории.
